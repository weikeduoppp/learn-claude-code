# 学习地图

## s19 到 s20

`s19` 解决的是“外部工具怎么标准接入”。

`s20` 解决的是“前面 19 章的机制，怎么重新放回一个完整可运行的 Agent 系统里”。

一句话记住：

> `s19` 管能力来源，`s20` 管全系统归位。

再压成一句：

> 从“能力可以接进来”，进入“所有能力都挂回同一个循环”。

---

## 本章解决什么问题

这章的敌人不是“缺某一个机制”，而是：

- 前 19 章的机制是拆着讲的
- 真实系统不会只开一个机制单独运行
- 很容易学会单点功能，却看不清它们各自挂在 loop 的什么位置

所以 `s20` 解决的不是“再发明一个新能力”，而是：

> 把前面所有机制按职责重新装回一个完整 harness。

## 核心设计

### 1. 这章真正教的不是“全部都有”，而是“全部各归其位”

`s20` 最容易看花眼，因为东西很多。  
但这章的本质不是“功能堆叠”，而是：

> 每个机制都挂在 loop 的某个固定位置。

要看清的是位置关系，不是工具列表长度。

### 2. harness 的主轴仍然是同一个 loop

最重要的事实是：

- 还是调用模型
- 还是检查 `tool_use`
- 还是执行工具
- 还是把结果写回 `messages`

也就是说：

> 前面 19 章没把 loop 替换掉，只是在 loop 周围逐步加壳。

### 3. 输入侧、调用侧、工具侧、返回侧被分层了

可以把 `s20` 粗分成四段：

- 输入前：用户输入、cron/background 通知、memory/skills/system prompt 组装
- 调用时：LLM 调用、压缩、错误恢复
- 工具前后：hooks、permission、background dispatch、MCP 调用
- 返回后：tool_result、task_notification、Stop hooks

这一层分工，比“记住一堆函数名”更重要。

### 4. 两层计划系统同时存在

`s20` 没有用 task system 替代 todo，也没有用 todo 替代 task。

它保留了两层：

- `todo_write`：当前会话内的轻量执行计划
- task graph：跨会话、可依赖、可认领的任务系统

这说明：

> 不同层级的问题，需要不同层级的计划工具。

### 5. delegation 也分层

`task` 和 `spawn_teammate` 都还在，但语义不同：

- `task`：一次性 subagent，用来隔离上下文
- `spawn_teammate`：长期 teammate，用来并行长期协作

所以 `s20` 并不是保留重复功能，而是保留不同 delegation 层级。

### 6. 最终系统的关键不是“功能齐全”，而是“边界清楚”

这一章真正体现 senior 工程设计的地方在于：

- hooks 不写进工具实现里
- permission 不和工具逻辑缠死
- compaction 不写死在 prompt 里
- cron 不写进 agent_loop 时间判断里
- MCP 不改主循环协议

这说明 `s20` 真正强调的是：

> 功能可以多，但边界不能乱。

## 为什么这样设计

### 为什么前面每章都不直接写成 `s20` 这样？

因为学习上不能一上来就看总装。  
如果没有前 19 章的拆解，你会看到一堆机制缠在一起，不知道每个存在的理由。

### 为什么 `s20` 还保留那么多“看似重复”的机制？

因为它们并不重复，只是分层不同：

- todo vs task
- subagent vs teammate
- background vs cron
- builtin tools vs MCP tools

### 为什么这章最重要的是“位置”而不是“功能数”？

因为真实系统出问题，大多数不是某个功能不存在，而是：

- 功能挂错层
- 边界混乱
- 控制流职责不清

### 为什么还能说“机制很多，循环一个”？

因为直到最后，真正没有被推翻的仍然是那个核心 loop。  
其余所有机制都是挂在它前后左右的 harness。

---

## 关键知识点

1. `s20` 教的是总装，不是单点新能力。
2. 真正要看清的是各机制挂在 loop 的哪个位置。
3. loop 本身没换，换的是外围壳越来越完整。
4. 计划、任务、协作、目录、插件、恢复、调度都是分层存在。
5. `s20` 的价值在于“边界清楚”，不是“功能越多越好”。

## 参考答案

### 第一轮参考答案

1. `s20` 新增的是把前面所有教学机制重新装配回同一个 Agent harness 的能力。它解决的是机制分散、看不清各自位置的问题。
2. 因为它没有发明新的单点能力，而是把已有能力重新组合回一个完整系统。
3. 因为 todo 是当前会话内轻量执行计划，task graph 是跨会话、可依赖、可认领的任务系统，层级不同。
4. 因为 `task` 是一次性 subagent delegation，`spawn_teammate` 是长期 teammate 协作，语义不同。
5. 提升的是系统完整性，不是模型推理能力。

### 第二轮参考答案

1. 因为真正的工程难点不是有没有这些能力，而是它们挂错层时整个系统会混乱。
2. 因为这些机制职责不同，应该分布在输入前、调用前后、工具执行前后、返回后等不同边界点上。
3. 因为直到最后，主循环仍然是“调模型 -> 看 tool_use -> 执行工具 -> 回写 messages”的结构。
4. 因为这章把所有机制都拉回来了；正确读法是按“输入侧、调用侧、工具侧、返回侧”分层读。

### 第三轮参考答案

1. 因为真正重要的是边界清楚、职责归位，而不是功能数量。
2. 因为不先拆开学，你根本分不清每个机制存在的理由和它应该挂的位置。
3. 它真正收束的是前面所有机制在同一个 loop 周围的相对位置和系统边界。
4. `s20` 的设计本质，是把前面所有分散机制按职责重新挂回同一个主循环，形成一个边界清楚的完整 Agent harness。
