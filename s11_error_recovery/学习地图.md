一句话记住：

> `s10` 管输入组织，`s11` 管失败恢复。

再压成一句：

> 从“怎么把 prompt 喂进去”，进入“喂进去之后出错了怎么继续”。

## 这章最该记住的 5 句话

1. `s11` 解决的是 agent 的韧性，不是工具能力问题。
2. 错误恢复必须先分类，再决定恢复动作。
3. 瞬态错误适合重试，结构性错误不能盲目重试。
4. 恢复逻辑必须有状态，否则会无限重试或重复恢复。
5. `s11` 的本质是：把失败从终点，变成主循环中的可治理状态。

## 一句话总结

`s11` 的核心不是“出错后打印日志”，而是让主循环在不同类型的失败面前，能够分类、恢复、继续，而不是直接退出。

s11 第一轮先答这 5 个，尽量用你自己的话，短答就行：
s11 相比 s10，新增的核心能力是什么？它解决的具体问题是什么？给agent添加了错误恢复能力, 3个错误路径, prompt_too_long, api瞬态错误, max_tokens 输出截断
“瞬态 API 错误” 的意思是：
这个错误是临时的、短时间内会自己恢复的 API 调用失败。

主循环的错误恢复机制。它把失败分成三类，再走三条不同恢复路径
max_tokens -> 升级 token / 续写
prompt_too_long -> reactive compact
429/529 -> 指数退避，必要时切 fallback model
s11 给 agent 加了“分类恢复”能力，让它在截断、上下文超限、瞬态故障下都能继续，而不是直接崩。


为什么错误不能统一“失败就重试”，而要先分类？ 便于针对性处理, 且有些路径返回不一致
不同错误需要的恢复动作根本不是同一种。
- 429/529 适合重试，因为问题可能会自己消失
- prompt_too_long 不能盲重试，因为上下文不会自己变短
- max_tokens 也不能盲重试，因为它会再次截断，必须先扩 token 或续写
所以关键不是“返回不一致”，而是：
错误的成因不同，恢复动作也不同。

RecoveryState 的作用是什么？为什么恢复逻辑必须有状态？
RecoveryState 是跨多轮恢复过程的状态容器，
错误恢复不是一次性 if/else，而是跨多轮重试的过程，所以必须显式记录状态：
- 有没有升级过 token
- 已经续写了几次
- 连续 529 次数
- 是否已经做过 reactive compact
- 当前用的是哪个 model
一句话：
恢复逻辑必须是有状态的。 恢复逻辑不是单次分支判断，而是带状态的恢复流程

with_retry() 和外层 try/except 分别处理什么类型的问题？with_retry只处理瞬态错误, try/except 处理非瞬态异常 处理is_prompt_too_long_error, 和未识别的错误
max_tokens 不属于异常处理，它是在拿到正常 response 之后单独检查 stop_reason，见 [code.py (line 356)](/Users/bytedance/Downloads/te/learn-claude-code/s11_error_recovery/code.py:356)

s11 提升的是模型能力，还是系统韧性？为什么？系统韧性, s11让系统能在错误中恢复
s11 没让模型更聪明，它让系统在面对真实世界的不稳定条件时更能撑住。
所以它提升的是系统韧性，不是推理能力。
你这一轮可以直接记住这句总总结：
s11 的本质不是“遇错重试”，而是把不同类型的失败接到主循环里，变成可分类、可恢复、可继续的运行状态。

1. 为什么 max_tokens 第一次发生时，不把截断输出立刻写进 messages，而是直接升级 max_tokens 重试？ 设计是：
第一次先重试同一请求，尽量保持原始上下文不变。
这是一种很稳的恢复策略，不轻易把半截输出污染进历史。
再更精确一点：
第一次先升级 max_tokens 重试，是为了保留原始请求语义，争取一次拿到完整答案，见 [code.py (line 356)](/Users/bytedance/Downloads/te/learn-claude-code/s11_error_recovery/code.py:356)。
如果第一次就把半截输出写进历史，会有两个问题：
- 历史被“残缺答案”污染
- 下一轮模型会把“续写半截文本”当成新任务上下文，而不是重新回答原请求
所以这一步的本质是：
优先修复容量，不急着接受半成品输出

2. 为什么 reactive_compact() 只允许做一次，而不是无限压缩下去？ 只给一次机会，避免死循环, 兜底也要有上限。
更本质的是：
如果压缩一次后还是太长，说明问题已经不是“再压一点就够了”，而是当前对话的语义体积已经超出可恢复范围，见 [code.py (line 338)](/Users/bytedance/Downloads/te/learn-claude-code/s11_error_recovery/code.py:338)。
继续无限压缩的问题是：
- 容易死循环
- 会越来越丢上下文
- 最后即使跑起来，也可能已经不是原任务了
所以这里不是单纯“设上限”，而是：
承认有些失败是不可继续恢复的。

3. 为什么 429/529 要放进 with_retry()，而不是和 prompt_too_long 一样全塞进外层 try/except？ with_retry只处理瞬态错误, try/except 处理非瞬态异常 , 错误的成因不同，恢复动作也不同。
- 429/529 适合重试，因为问题可能会自己消失
- prompt_too_long 不能盲重试，因为上下文不会自己变短
with_retry() 专门封装可重试的瞬态故障
外层 try/except 专门处理不能靠重复调用自行消失的问题

第三轮我直接继续问 4 个收束题：
1. s11 里，什么是“瞬态故障”，什么是“结构性故障”？ 瞬态故障: 可重试的问题 结构性故障: 不能靠重复调用自行消失的问题
瞬态故障：外部环境暂时不稳定，重复同一请求有机会成功，比如 429/529
结构性故障：当前请求本身就有问题，不改变请求条件就不会自己变好，比如 prompt_too_long，以及 max_tokens 这种“容量不够”的情况

2. 为什么 continuation prompt 要作为一条新的 user message 注入，而不是偷偷改写上一条 assistant 输出？告诉模型
continuation prompt 要变成一条新的 user message，是因为它本质上是对下一轮生成行为的显式指令，见 [code.py (line 366)](/Users/bytedance/Downloads/te/learn-claude-code/s11_error_recovery/code.py:366)。
如果偷偷改上一条 assistant 输出，会有两个问题：
- 篡改历史，破坏对话记录的真实性
- 模型看不到“现在用户要求你继续写”的新指令边界
所以这里的本质是：
续写不是修改过去，而是为下一轮生成增加一条明确控制指令。

3. 为什么说 s11 的恢复逻辑应该挂在 loop 外围，而不是塞进 tool 内部或 prompt 组装内部？
这些核心东西没变：
- 还是同一个 while True
- 还是一轮轮调用模型
- 还是看 stop_reason
- 还是 tool_use -> 执行工具 -> 把结果写回 messages -> 继续下一轮
变的是：
- 调模型前后多了一层“错误分类和恢复”

s11 处理的是LLM 调用这一层的失败语义，不是某个 tool 的局部行为，也不是 prompt 生产的问题。主循环里真正会遇到 stop_reason、API 异常、上下文超限的地方，就是模型调用外围，见 [code.py (line 333)](/Users/bytedance/Downloads/te/learn-claude-code/s11_error_recovery/code.py:333)。
所以：
- 放进 tool 内部太晚了，因为很多错误发生在 tool 之前
- 放进 prompt 组装里也不对，因为 prompt assembly 不负责调用失败后的控制流
- 挂在 loop 外围才正好卡住“每轮请求”的统一入口
一句话：
恢复逻辑属于调度层，不属于工具层，也不属于 prompt 层。
