# 学习地图

## s18 到 s19

`s18` 解决的是“多个 Agent 在哪里工作互不干扰”。

`s19` 解决的是“Agent 的工具能力为什么必须都手写，外部服务怎么标准接入”。

一句话记住：

> `s18` 管目录隔离，`s19` 管能力接入。

再压成一句：

> 从“在哪干活”，进入“拿什么工具干活”。

---

## 本章解决什么问题

这章的敌人不是“工具不够多”，而是：

- 所有工具都要手写，扩展成本高
- 外部系统接入没有统一协议
- 多个外部服务容易发生工具名冲突
- 工具池不再是静态常量，而会在运行时变化

所以 `s19` 解决的不是“再多加几个工具函数”，而是：

> 把外部能力通过标准协议接进 Agent，让工具池动态扩展。

---

## 核心设计

### 1. MCP 解决的是扩展接口，不是具体业务

这一章最重要的抽象是：

> Agent 不需要知道工具是谁写的，只需要知道如何发现和调用。

所以 MCP 的本质不是“docs server”或“deploy server”，而是统一外部能力接入方式。

### 2. `connect_mcp()` 只负责连接和发现

`connect_mcp()` 做的不是执行业务，而是：

- 连接 server
- 拿到工具定义
- 把 client 放进当前连接表

这说明接入层和工具执行层已经分开了。

### 3. 工具池必须动态组装

`assemble_tool_pool()` 的核心意义是：

> 每轮都根据当前已连接 MCP server，重新拼出真实可用的工具集合。

这和前面固定工具列表的章节不同，因为工具池现在是会变的。

### 4. `mcp__server__tool` 是命名冲突隔离层

如果不同 server 都有 `search` 工具，直接平铺就会冲突。  
所以需要前缀命名空间：

- `mcp__docs__search`
- `mcp__deploy__search`

这说明 `s19` 除了接入能力，还解决了：

> 多服务同名工具的隔离问题。

### 5. 规范化名字是安全边界的一部分

`normalize_mcp_name()` 不是为了好看，而是为了：

- 防特殊字符
- 防命名注入
- 保持工具名稳定可引用

所以本章除了扩展性，也很强调接入边界安全。

### 6. 动态工具池会破坏 prompt cache 的前提

之前很多章节都能缓存 system prompt。  
到了 `s19`，连接新的 MCP server 之后，工具池变了，prompt 也必须跟着变。

这说明：

> prompt cache 依赖“工具集合稳定”，而 MCP 打破了这个前提。

所以教学版在这里去掉缓存，是为了保持工具池和 prompt 同步。

## 为什么这样设计

### 为什么不直接把外部工具硬编码进代码？

因为那样每接一个新系统都要：

- 写新 schema
- 写新 handler
- 改主工具池

这违背了插件化初衷。

### 为什么一定要有 `assemble_tool_pool()`？

因为现在工具来源不止一个：

- 内置工具
- 外部 MCP 工具

所以系统需要一个统一汇总入口，把它们拼成“当前这一轮的真实工具池”。

### 为什么 MCP 工具名必须带 server 前缀？

因为插件化之后，工具重名是常态，不是边缘情况。  
前缀命名是 namespace 机制，不是装饰。

### 为什么只有 Lead 用 MCP 工具？

这是教学简化。  
这章主要先教“外部能力如何接入主工具池”，而不是把整个团队权限传播和配置继承也一起展开。

## 关键知识点

1. `s19` 升级的是能力接入模型，不是目录模型。
2. MCP 的核心是“发现 + 调用”协议，不是某个具体 server。
3. `connect_mcp()` 负责连接和发现，`assemble_tool_pool()` 负责组装可用工具池。
4. `mcp__server__tool` 解决多服务工具重名问题。
5. 动态工具池意味着 system prompt 也必须动态更新。
6. 名称规范化是接入安全边界的一部分。

---

### 相对 `s18`

`s18` 解决“在哪工作”。

## 扩展点与局限

### 教学版的扩展点

- 支持真实 stdio/server 通信
- 把 MCP 工具开放给队友
- 引入权限系统和 annotation 结构
- 加强连接失败与断线恢复

### 教学版的局限

- 用 mock server 代替真实 transport
- 只演示最小发现/调用模型
- 未展开复杂权限和认证
- 未覆盖多 transport 差异

## 参考答案

### 第一轮参考答案

1. `s19` 新增的是通过 MCP 协议动态发现和接入外部工具的能力。它解决的是外部服务扩展成本高、工具接入不统一的问题。
2. 因为每接一个外部服务都要重写 schema、handler 和工具池组装，维护成本会迅速失控。
3. `MCPClient` 负责抽象发现和调用，`connect_mcp()` 负责连接 server 并注册 client，`assemble_tool_pool()` 负责把内置工具和 MCP 工具拼成当前真实可用工具池。
4. 因为不同 server 会有同名工具，必须通过命名空间隔离冲突。
5. 提升的是能力接入能力，不是模型推理能力。

### 第二轮参考答案

1. 因为连接层和业务执行层应该分离，前者负责可用能力发现，后者负责真正的工具调用。
2. 因为当前已连接的 server 会变化，工具池不是静态的。
3. 因为 server 名和工具名最终会进入统一工具命名空间，必须防止特殊字符和命名注入。
4. 因为主循环协议没变，变的是 loop 外围多了动态工具池组装。

### 第三轮参考答案

1. 因为真正的变化是工具集合不再固定，而会根据当前连接状态动态变化。
2. 因为 prompt 里会包含当前可用工具说明，工具池变化就意味着 prompt 也要变化，缓存前提被打破。
3. 因为现在所有机制都已经存在，但还没有统一合回一个完整 harness。
4. `s19` 的设计本质，是把 Agent 的能力来源从固定内置工具升级成可动态发现和组装的外部能力池。
