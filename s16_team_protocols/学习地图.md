# 学习地图

## s15 到 s16

`s15` 解决的是“多个 Agent 怎么长期通信协作”。

`s16` 解决的是“队友之间不是只会发散消息，而是要有结构化协议和握手”。

一句话记住：

> `s15` 管通信，`s16` 管协议。

再压成一句：

> 从“能发消息”，进入“消息之间要有请求-响应关系和状态”。

---

## 本章解决什么问题

这章的敌人不是“不会通信”，而是：

- 队友之间只有松散文本消息
- 关机这种高风险动作不能靠口头约定
- 计划审批这种流程没有 request-response 结构
- 系统无法追踪一条请求当前是 pending 还是已经处理完

所以 `s16` 解决的不是“再多几个消息类型”，而是：

> 把队友通信从散乱文本，升级成带 request_id 的结构化握手协议。

---

## 核心设计

### 1. 协议的核心不是消息内容，而是状态追踪

`ProtocolState` 记录的不是“说了什么”，而是：

- 这是谁发起的请求
- 发给谁
- 是什么类型
- 当前是 pending 还是 resolved

这说明本章的本质不是聊天，而是：

> 把队友交互升级成可追踪的流程状态。

### 2. request_id 是整条协议链的锚点

没有 `request_id`，请求和响应就只是两条普通消息。  
有了 `request_id`，系统才能把：

- shutdown request
- shutdown response

或

- plan approval request
- plan approval response

关联成一条完整事务链。

### 3. dispatch_message 的本质是按类型路由，不再平铺处理

`handle_inbox_message()` 做的不是“收到消息就拼进上下文”，而是：

> 不同类型的消息走不同处理器。

这意味着协议消息和普通文本消息，从这一章开始被系统正式区分。

### 4. match_response 不只是找 ID，还要做类型校验

`match_response()` 最关键的不只是 `request_id` 匹配，还包括“这个 response 是否匹配这个 request 的类型”，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s16_team_protocols/code.py:392)。

所以它解决的是：

- 防止错配
- 防止重复处理
- 防止一条响应意外更新错误的请求状态

### 5. inbox 读取要统一入口

`consume_lead_inbox()` 的意义，不是少写点代码，而是：

> 防止消息被读走了，但协议状态没有更新。

所以这章开始强调一个重要设计原则：

协议消息的消费和状态更新必须绑定。

### 6. 队友 idle loop 是协议的运行前提

如果队友做完活立刻退出，就收不到后续的 shutdown_request 或 plan response。  
所以 `s16` 的 idle loop 不是附加小优化，而是协议能工作的重要前提。

而且现在教学版也补上了 `idle_notification`：

- 队友进入 idle 时会显式通知 Lead
- Lead 知道它不是“没消息”，而是“当前空闲可分配”
- 这样 shutdown、继续派活、观察团队空闲状态都更自然

## 为什么这样设计

### 为什么不能继续只靠普通文本消息？

因为普通文本消息没有：

- 关联键
- 状态
- 类型校验
- 一致的处理入口

所以它能表达“交流”，但不能稳定表达“协议”。

### 为什么 protocol state 要独立存储，而不是只靠 inbox 历史回看？

因为 inbox 消息会被消费掉。  
如果没有独立状态表，系统就无法持续知道这条请求现在的状态。

### 为什么关机和计划审批能复用同一套机制？

因为它们的共同结构是一样的：

- 一方发 request
- 另一方发 response
- 中间通过 request_id 关联
- 最终状态从 pending 进入 approved/rejected

这就是协议抽象的力量。

## 关键知识点

1. `s16` 升级的是协作协议，不是消息总线本身。
2. `request_id` 是请求和响应的关联锚点。
3. `ProtocolState` 让协议有持久状态，而不是只靠消息文本。
4. `match_response()` 负责关联、校验和状态推进。
5. `consume_lead_inbox()` 让消息消费和协议状态更新绑定。
6. idle loop 是协议能够持续工作的前提。
7. `idle_notification` 让 Lead 显式知道队友空闲，而不是靠猜测。

s16 新增的是request-response 协议能力 + 协议状态追踪。
不只是“消息更结构化”，而是系统开始能追踪一条请求从 pending 到 approved/rejected 的流转。

2. 为什么队友之间不能继续只靠普通文本消息，而要上协议？

- 一致的处理入口

把协议请求变成可追踪的外部状态记录。
重点不是字段多，而是系统能独立知道：
- 谁发起的
- 发给谁

- 现在是否已经处理完

有了 `request_id`，系统才能把：
- shutdown request
- shutdown response
或
- plan approval request
- plan approval response
关联成一条完整事务链。
5. `s16` 提升的是模型能力，还是协作控制能力？为什么？协作控制能力 升级的是协作协议，不是消息总线本身。
模型没变聪明，变的是多 Agent 之间的协作被系统规则约束了，不再只靠自然语言默契。

match_response() 不只是“找到这条请求”，而是要确认“这条响应是不是这类请求该收到的响应”。
2. 为什么 `consume_lead_inbox()` 要统一处理，而不是哪里想读 inbox 就哪里读？ 防止消息被读走了，但协议状态没有更新。

所以 `s16` 的 idle loop 不是附加小优化，而是协议能工作的重要前提。
4. `s16` 为什么还能继续说 `loop unchanged`？通信协议也是放在loop外层, 
更标准的说法是：
s16 仍然能说 loop unchanged，因为每个 Agent 内部还是同一套协议：

1. 为什么说 `s16` 的核心不是“消息更多了”，而是“消息之间有了状态关系”？同一个request_id消息一来一回,有了状态更新.

- 中间靠 request_id 关联

所以这章教的不是“关机协议”或“计划审批协议”本身，而是更底层的模式：把多 Agent 互动抽象成 request-response 状态机。

## 参考答案

### 第一轮参考答案

1. `s16` 新增的是 request-response 协议能力。它解决的是关机、审批这类动作不能只靠松散消息，而要有结构化状态追踪。
2. 因为普通文本没有 request_id、没有状态流转、没有类型边界，无法稳定承载高风险协作流程。
3. `ProtocolState` 是协议状态容器，用来记录请求的发起者、接收者、类型、状态和 payload。
4. 因为 request_id 是整条协议链的关联键，请求出去时带着它，响应回来时也带着它，系统才能正确匹配。
5. 提升的是协作控制能力，不是模型推理能力。模型没变聪明，只是系统更会管理队友之间的协商流程。

### 第二轮参考答案

1. 因为只按 request_id 找还不够，类型校验能避免一条响应错误地更新到不匹配的请求上。
2. 因为协议消息的消费和状态推进必须保持一致，统一入口能避免消息被读走但状态没更新。
3. 因为队友如果做完就退出，就收不到后续协议消息；idle loop 让队友在完成当前工作后仍能继续参与协议。
4. 因为每个 Agent 的 loop 结构没变，变的是 loop 外围多了一层协议路由和状态管理。

### 第三轮参考答案

1. 因为新增的不是消息数量，而是消息被纳入了 request-response 状态机。
2. 它们都是一方发起 request，另一方回 response，通过 request_id 关联，并最终推进状态。
3. 因为协议解决了“怎么协调”，但还没解决“任务谁来主动领取和推进”。
4. `s16` 的设计本质，是把多 Agent 协作从松散聊天升级成带 request-response 状态机的结构化流程。
