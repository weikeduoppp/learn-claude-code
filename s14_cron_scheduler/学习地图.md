# 学习地图

## s13 到 s14

`s13` 解决的是“慢操作怎么不阻塞主循环”。

`s14` 解决的是“不是现在立刻做，而是在未来某个时间点自动触发”。

一句话记住：

> `s13` 管异步完成，`s14` 管定时开始。

再压成一句：

> 从“任务启动后慢慢跑”，进入“任务什么时候自动开始跑”。

---

## 本章解决什么问题

这章的敌人不是“不会后台执行”，而是：

- 后台任务仍然需要人手动发起
- 周期性工作不能每次都靠用户来推一下
- 调度和执行还没有真正解耦
- 任务需要跨会话保留定义，而不是每次重建

所以 `s14` 解决的不是“再加一个 tool”，而是：

> 把触发时机从“用户输入”升级成“时间表驱动”。

## 核心设计

### 1. 触发和执行必须分离

这章最重要的抽象，不是 cron 语法，而是：

> 决定“该不该触发” 和 真正“去执行” 不能绑死在一起。

所以它拆成了四层，见 [README.md](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/README.md:40)：

1. Scheduler：看时间
2. Queue：存已触发任务
3. Queue Processor：趁 Agent 空闲时交付
4. Consumer：`agent_loop()` 真正消费

这个拆法的意义是：

- 调度器不用懂 LLM
- agent_loop 不用自己看时间
- 中间靠队列解耦

### 2. CronJob 是“未来工作定义”，不是立刻执行

`CronJob` 不是任务结果，也不是后台任务实例，它更像“未来某时要注入的一条工作定义”，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:353)。

重点字段：

- `id`：任务身份
- `cron`：时间表达式
- `prompt`：到点后注入给 Agent 的消息
- `recurring`：是否周期性
- `durable`：是否持久化到磁盘

一句话：

> `CronJob` 描述的是“何时触发什么工作”，不是“工作如何完成”。

### 3. 调度线程只负责“发现到点”

`cron_scheduler_loop()` 每秒轮询一次，匹配到时间后把 job 放进 `cron_queue`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:521)。

它**不会直接执行任务**。  
它只负责：

- 检查现在时间
- 判断哪些 job 命中
- 把命中的 job 送进队列

这背后的设计原则是：

> 调度器只负责判定时机，不负责消费任务。

### 4. 队列处理器负责“什么时候安全交付”

仅仅把 job 放进队列还不够。  
系统还要判断：Agent 当前是不是空闲，可以安全启动一轮处理。

这就是 `queue_processor_loop()` 的作用，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:775)。

它通过 `agent_lock` 做了一个很关键的控制：

- 如果 Agent 正在忙，就先别交付
- 如果 Agent 空闲，再拉起一轮 `agent_loop`

所以 queue processor 解决的是：

> “到点了” 不等于 “现在立刻能执行”，中间还要做交付时机控制。

### 5. 真正进入主循环的是“已触发任务”，不是时间检查逻辑

`agent_loop()` 并不自己检查时间。  
它只在开头消费 `cron_queue`，把已经触发的任务注入成 user message，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:688)。

这说明：

- 时间判断在 loop 外面
- loop 只消费“已经被调度好的工作”

一句话：

> 主循环消费的是调度结果，不是调度过程。

### 6. Durable 不是“进程关闭也会自动跑”

这是本章最容易误解的一点。

`durable=True` 的意思只是：

- job 定义写进 `.scheduled_tasks.json`
- 下次 Agent 启动时可以恢复

它**不意味着**进程关闭后 cron 还会自己跑。  
README 也明确写了这个前提，见 [README.md](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/README.md:111)。

所以 durable 的真实含义是：

> 调度定义跨重启保留，不是调度器跨进程常驻。

## 为什么这样设计

### 为什么需要 Queue，不能调度线程直接调用 agent_loop？

因为调度器和执行器不是一个责任层。

如果调度线程直接拉起 agent_loop，会带来几个问题：

- 触发判断和执行耦合
- Agent 忙时不好处理
- 多个 job 同时到点时难以缓冲

所以中间必须有 `cron_queue`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:363)。

一句话：

> Queue 不是装饰，而是调度与执行之间的缓冲层。

### 为什么还要 queue processor，不能 agent_loop 自己轮询队列？

因为 `agent_loop()` 本来是“有一轮输入时才跑一次”的。  
如果想让 cron 在用户不输入时也能自动生效，就必须有一个外部组件负责“空闲时拉起一轮”。

这就是 queue processor 的职责，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:775)。

### 为什么要用 `agent_lock`？

因为系统必须防止：

- 用户正在和 Agent 交互时
- queue processor 又并发拉起一轮 cron 处理

所以它不是普通锁而已，而是：

> Agent 是否空闲 的并发控制开关。

### 为什么要做 cron 校验？

因为坏表达式如果进入调度系统，会把问题从“注册时可报错”变成“运行时随机炸线程”。

所以 `validate_cron()` 的作用不是用户体验优化，而是调度器边界保护，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:450)。

## 关键知识点

1. `s14` 升级的是触发模型，不是执行模型。
2. 调度器负责看时间，不负责执行任务。
3. queue processor 负责在 Agent 空闲时交付已触发任务。
4. `agent_loop()` 消费的是已调度任务，不自己看时间。
5. durable 持久化的是任务定义，不是活着的调度线程。
6. `minute_marker` 是为了防止同一分钟重复触发。
7. cron 校验是调度器的输入边界保护。

## 扩展点与局限

### 教学版的扩展点

- 可以支持更多 cron 语法
- 可以把 `cron_queue` 换成更正式的队列实现
- 可以增加优先级、失败重试、观察指标
- 可以把调度器和执行器拆成独立进程
- 可以做 missed run 补偿策略

### 教学版的局限

- 调度线程依赖当前进程存活
- durable 不能保证“进程关闭时也准点执行”
- 队列只是内存 list，不是可靠消息队列
- 没有复杂优先级和回压控制
- 没有分布式锁或多实例协调

这些不是 bug，而是教学版故意保留的真实系统问题。

### 第二轮

1. 为什么 `minute_marker` 很关键？如果没有它会发生什么？调度器每秒轮询一次,而 cron 通常按分钟命中,同一分钟内会多次命中同一个 job;没有标记就会重复入队。"YYYY-MM-DD HH:MM" 是 date-aware:如果只看分钟("HH:MM"),第二天同一时刻会与昨天相同,被 _last_fired 误判为"已触发"而跳过;带上日期后,每天同一时刻是不同的 marker,既防止同分钟重复触发,又不跨天误判。
2. 为什么 `durable` 持久化的是 job 定义，而不是“活着的调度线程”？ 关闭进程, 也会停止工作, 下次会话, 会拉起job定义
3. 为什么 `queue processor` 要先判断 Agent 是否空闲，而不是一触发就强行塞进主循环？ 
"已经到点" ≠ "现在适合执行"。如果 Agent 正在处理你的请求，一触发就强行塞进去会打乱当前对话、造成并发冲突；所以用 agent_lock.acquire(blocking=False) 判断空闲，空闲才交付，忙就等下轮。

loop 里只有"消费 → 调模型 → 处理 tool_use → 写回 messages"，scheduler 和 queue 都在外面，主循环协议没变。

## 参考答案

### 第一轮参考答案

1. `s14` 新增的是时间驱动调度能力。它解决的是任务不该总靠用户手动发起，而应该能在未来某个时间点或周期自动触发。
2. 因为“到点判断”和“真正执行”不是一个责任层。拆成 `scheduler + queue + queue processor` 之后，系统才能既判断时间，又缓冲已触发任务，还能在 Agent 空闲时安全交付。
3. `CronJob` 是未来工作的定义，描述“什么时候触发什么 prompt”；`cron_queue` 是已触发任务的缓冲区；`queue processor` 负责在合适时机把这些已触发任务送进主循环。
4. 因为 scheduler 的职责只是看时间和判定命中，不应该直接接管 Agent 执行。如果它直接拉起 Agent，就会把时间判断、并发控制、执行交付耦合在一起。
5. 提升的是触发调度能力，不是模型能力。模型没有更聪明，执行器也没有换掉，变化的是系统终于知道“什么时候自动开始做事”。

### 第二轮参考答案

1. 因为 scheduler 每秒轮询一次，而 cron 通常按分钟匹配；如果没有 `minute_marker`，同一分钟命中的 job 会被重复放进队列很多次。
2. 因为磁盘能保存的是“任务定义状态”，不能保存一个正在运行的内存线程。`durable` 的意义是重启后重新加载 job，而不是让旧线程继续活着。
3. 因为“已经到点”不等于“现在适合执行”。如果 Agent 正在处理用户请求，还强行塞入 cron 工作，就会打乱当前对话或造成并发冲突。
4. 因为主循环协议没变。`agent_loop()` 仍然只是消费输入、调模型、处理 `tool_use`、写回 `messages`；变化的是 loop 外面多了一层时间触发和安全交付机制。

### 第三轮参考答案

1. 因为 cron 表达式只是输入形式，真正重要的是系统学会了把“触发条件判断”和“任务执行”拆开。没有这个分层，cron 语法再完整也只是把耦合写得更复杂。
2. loop 外面的是时间检查、触发判定、队列缓冲、空闲交付；loop 里面仍然是把工作注入 `messages`、调用模型、执行工具、推进会话。
3. 因为 `s14` 解决的是“什么时候做”，但还没解决“谁来做”。一旦系统能定时触发工作，下一步自然就是把工作分配给不同 Agent 协作执行，这就是 `s15`。
4. `s14` 的设计本质，是把未来时刻触发的工作做成可持久化、可缓冲、可安全交付的外部调度事件，再接回原来的 Agent 主循环。
