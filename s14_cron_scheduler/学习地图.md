# 学习地图

## s13 到 s14

`s13` 解决的是“慢操作怎么不阻塞主循环”。

`s14` 解决的是“不是现在立刻做，而是在未来某个时间点自动触发”。

一句话记住：

> `s13` 管异步完成，`s14` 管定时开始。

再压成一句：

> 从“任务启动后慢慢跑”，进入“任务什么时候自动开始跑”。

---

## 本章解决什么问题

这章的敌人不是“不会后台执行”，而是：

- 后台任务仍然需要人手动发起
- 周期性工作不能每次都靠用户来推一下
- 调度和执行还没有真正解耦
- 任务需要跨会话保留定义，而不是每次重建

所以 `s14` 解决的不是“再加一个 tool”，而是：

> 把触发时机从“用户输入”升级成“时间表驱动”。

## 核心设计

### 1. 触发和执行必须分离

这章最重要的抽象，不是 cron 语法，而是：

> 决定“该不该触发” 和 真正“去执行” 不能绑死在一起。

所以它拆成了四层，见 [README.md](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/README.md:40)：

1. Scheduler：看时间
2. Queue：存已触发任务
3. Queue Processor：趁 Agent 空闲时交付
4. Consumer：`agent_loop()` 真正消费

这个拆法的意义是：

- 调度器不用懂 LLM
- agent_loop 不用自己看时间
- 中间靠队列解耦

### 2. CronJob 是“未来工作定义”，不是立刻执行

`CronJob` 不是任务结果，也不是后台任务实例，它更像“未来某时要注入的一条工作定义”，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:353)。

重点字段：

- `id`：任务身份
- `cron`：时间表达式
- `prompt`：到点后注入给 Agent 的消息
- `recurring`：是否周期性
- `durable`：是否持久化到磁盘

一句话：

> `CronJob` 描述的是“何时触发什么工作”，不是“工作如何完成”。

### 3. 调度线程只负责“发现到点”

`cron_scheduler_loop()` 每秒轮询一次，匹配到时间后把 job 放进 `cron_queue`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:521)。

它**不会直接执行任务**。  
它只负责：

- 检查现在时间
- 判断哪些 job 命中
- 把命中的 job 送进队列

这背后的设计原则是：

> 调度器只负责判定时机，不负责消费任务。

### 4. 队列处理器负责“什么时候安全交付”

仅仅把 job 放进队列还不够。  
系统还要判断：Agent 当前是不是空闲，可以安全启动一轮处理。

这就是 `queue_processor_loop()` 的作用，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:775)。

它通过 `agent_lock` 做了一个很关键的控制：

- 如果 Agent 正在忙，就先别交付
- 如果 Agent 空闲，再拉起一轮 `agent_loop`

所以 queue processor 解决的是：

> “到点了” 不等于 “现在立刻能执行”，中间还要做交付时机控制。

### 5. 真正进入主循环的是“已触发任务”，不是时间检查逻辑

`agent_loop()` 并不自己检查时间。  
它只在开头消费 `cron_queue`，把已经触发的任务注入成 user message，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:688)。

这说明：

- 时间判断在 loop 外面
- loop 只消费“已经被调度好的工作”

一句话：

> 主循环消费的是调度结果，不是调度过程。

### 6. Durable 不是“进程关闭也会自动跑”

这是本章最容易误解的一点。

`durable=True` 的意思只是：

- job 定义写进 `.scheduled_tasks.json`
- 下次 Agent 启动时可以恢复

它**不意味着**进程关闭后 cron 还会自己跑。  
README 也明确写了这个前提，见 [README.md](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/README.md:111)。

所以 durable 的真实含义是：

> 调度定义跨重启保留，不是调度器跨进程常驻。

## 为什么这样设计

### 为什么需要 Queue，不能调度线程直接调用 agent_loop？

因为调度器和执行器不是一个责任层。

如果调度线程直接拉起 agent_loop，会带来几个问题：

- 触发判断和执行耦合
- Agent 忙时不好处理
- 多个 job 同时到点时难以缓冲

所以中间必须有 `cron_queue`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:363)。

一句话：

> Queue 不是装饰，而是调度与执行之间的缓冲层。

### 为什么还要 queue processor，不能 agent_loop 自己轮询队列？

因为 `agent_loop()` 本来是“有一轮输入时才跑一次”的。  
如果想让 cron 在用户不输入时也能自动生效，就必须有一个外部组件负责“空闲时拉起一轮”。

这就是 queue processor 的职责，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:775)。

### 为什么要用 `agent_lock`？

因为系统必须防止：

- 用户正在和 Agent 交互时
- queue processor 又并发拉起一轮 cron 处理

所以它不是普通锁而已，而是：

> Agent 是否空闲 的并发控制开关。

### 为什么要做 cron 校验？

因为坏表达式如果进入调度系统，会把问题从“注册时可报错”变成“运行时随机炸线程”。

所以 `validate_cron()` 的作用不是用户体验优化，而是调度器边界保护，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s14_cron_scheduler/code.py:450)。

## 关键知识点

1. `s14` 升级的是触发模型，不是执行模型。
2. 调度器负责看时间，不负责执行任务。
3. queue processor 负责在 Agent 空闲时交付已触发任务。
4. `agent_loop()` 消费的是已调度任务，不自己看时间。
5. durable 持久化的是任务定义，不是活着的调度线程。
6. `minute_marker` 是为了防止同一分钟重复触发。
7. cron 校验是调度器的输入边界保护。

## 和前后章节的关系

### 相对 `s13`

`s13` 已经让系统学会：

- 任务可以异步执行
- 完成后可以回注通知

但还缺一个问题：

> 这些任务什么时候开始，不该永远依赖用户手动触发。

所以：

- `s13` 管异步执行
- `s14` 管时间触发

### 为什么自然通向 `s15`

到了 `s14`，系统已经有：

- 任务
- 后台执行
- 定时触发

下一步自然就不再是“什么时候做”，而是：

> 谁来做？

这正是 `s15` 的 agent teams。

## 扩展点与局限

### 教学版的扩展点

- 可以支持更多 cron 语法
- 可以把 `cron_queue` 换成更正式的队列实现
- 可以增加优先级、失败重试、观察指标
- 可以把调度器和执行器拆成独立进程
- 可以做 missed run 补偿策略

### 教学版的局限

- 调度线程依赖当前进程存活
- durable 不能保证“进程关闭时也准点执行”
- 队列只是内存 list，不是可靠消息队列
- 没有复杂优先级和回压控制
- 没有分布式锁或多实例协调

这些不是 bug，而是教学版故意保留的真实系统问题。

## 运行观察点

启动命令：

```bash
python3 s14_cron_scheduler/code.py
```

建议观察这些现象：

- 启动时出现 `[cron] scheduler thread started`
- 输入注册命令后出现 `[cron register] ...`
- 到点后出现 `[cron fire] ...`
- Agent 空闲时出现 `[queue processor] delivering scheduled work`
- 然后 `agent_loop()` 注入 `[Scheduled] ...`
- durable job 会写入 `.scheduled_tasks.json`

建议实验顺序：

1. 先注册一个每 2 分钟触发的 recurring job
2. 再注册一个 one-shot job
3. `list_crons` 看状态
4. 等待到点，观察 fire -> queue processor -> inject 的完整链条
5. 重启程序，确认 durable job 会被重新加载

## 一句话总结

`s14` 的核心不是“支持 cron 表达式”，而是把“时间到了”这件事做成独立的调度事件，再通过队列和空闲检测安全地交付给 Agent 主循环。
