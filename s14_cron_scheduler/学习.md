## 【修订版(基于最新 s14 代码)】

Q1: 四层模型?
A: 1. Scheduler(cron_scheduler_loop):每秒轮询,判断时间,命中的 job 放进 cron_queue——只看时间,不懂 LLM。2. Queue(cron_queue):已触发任务的缓冲区,调度线程写、queue processor 交付、agent_loop 消费。3. Queue Processor(queue_processor_loop):每 0.2s 检查队列非空且 Agent 空闲(agent_lock 非阻塞 acquire 成功),就拉起一轮 agent_loop。4. Consumer(agent_loop):不检查时间,只在开头 consume_cron_queue,把 job.prompt 注入成 "[Scheduled] ..." user 消息。
为什么必须有 Queue:① 解耦——调度器不碰执行,agent_loop 不看时间;② 缓冲——多个 job 同时到点时有地方排队;③ Agent 忙时可以等,不会直接打断当前回合;④ 保持 agent_loop 协议不变(loop unchanged:主循环只是多了个消费步骤)。
原回答"保证一个loop"方向对,补上理由:没有 Queue,调度线程直接拉起 agent_loop 会把触发判断、并发控制、执行交付耦合在一起,Agent 忙时也无法处理。

Q2: DOM/DOW 语义?
A: 分钟、小时、月必须全部匹配;DOM 和 DOW 的规则是:两个都被约束(都不是 *)时,任一匹配即可(OR);只有 DOM 被约束就看 DOM;只有 DOW 被约束就看 DOW;都未约束直接 True。
dow_val 转换:Python weekday() 周一=0…周日=6 → cron 的周日=0…周六=6,(x+1)%7 得到 Monday=1…Sunday=0。不转换的话,cron 的 "0"(周日)永远匹配不上 Python 的周日(6),周一也会错位成周二。
原回答只抄了注释,没写出 OR 语义和转换结果。

Q3: minute_marker?
A: 调度器每秒轮询一次,而 cron 通常按分钟命中,同一分钟内会多次命中同一个 job;没有标记就会重复入队。
"YYYY-MM-DD HH:MM" 是 date-aware:如果只看分钟("HH:MM"),第二天同一时刻会与昨天相同,被 _last_fired 误判为"已触发"而跳过;带上日期后,每天同一时刻是不同的 marker,既防止同分钟重复触发,又不跨天误判。

Q4: validate_cron?
A: 两个时机:① schedule_job 注册前(非法表达式直接返回错误,不进系统);② load_durable_jobs 启动加载时(非法 job 打印 "skipping invalid job" 并跳过,不影响启动)。
为什么是输入边界保护:坏表达式如果进了系统,问题会从"注册时就能报错"变成"运行时在调度线程里随机炸"——cron_scheduler_loop 每秒要解析所有 job,一个坏表达式可能让匹配抛异常。校验把失败提前到入口处,失败模式可控、报错清晰;加载时的校验保证一个坏磁盘文件不会拖垮启动。原回答"保证表达式合法"方向对,补上"什么时候跑"和"为什么是边界"。

Q5: durable?
A: 持久化的是任务定义(job 的 id/cron/prompt/recurring/durable,写入 .scheduled_tasks.json),不是"定时循环"本身,更不是活着的线程。
进程关闭后不会再触发——调度线程是 daemon,进程退出它就停;下次启动时 load_durable_jobs 恢复定义,调度器重新开始轮询,到点继续触发。
原回答"定时循环执行"不对:定时循环(调度线程)不持久,持久的是 job 定义;"下次循环会话会继续"对,但要说清楚恢复的是定义,不是补偿执行。

Q6: 空闲判断与互斥?
A: queue_processor_loop 每 0.2s:先 has_cron_queue(),再 agent_lock.acquire(blocking=False)——抢到锁说明没有其他回合在跑,抢不到说明 Agent 忙,continue 下轮再试。
互斥:用户输入的主循环用 with agent_lock: 包住 run_agent_turn_locked(query);queue processor 用非阻塞 acquire。同一时刻只有一个回合在跑:用户输入时 queue processor 抢不到锁;queue processor 执行时用户输入要等锁释放。原回答"agent_lock"正确,补上非阻塞 acquire 和两处抢锁。

Q7: 单 job 异常?
A: cron_scheduler_loop 里每个 job 的匹配/入队/删除包在 try/except 里,单个 job 抛异常只打印 "[cron error] {job.id}: {e}",循环继续,其他 job 正常触发。
为什么不会拖垮:没有 try/except,一个 job 的异常会冒泡出 while True,整个调度线程崩溃退出,所有定时任务都停。单 job 隔离 = 把故障边界缩到最小,一个坏任务只影响它自己。

Q8: 教学版 vs CC 差距?
A: ① 工具:教学版 schedule_cron/list_crons/cancel_cron;CC 是 CronCreate/CronDelete/CronList,受 feature gate + GrowthBook 运行时开关控制。② 存储与并发:教学版只有 .scheduled_tasks.json;CC 还有 .scheduled_tasks.lock 防止同项目多 session 重复触发 + chokidar 观察文件变更。③ 抖动(防惊群):CC 重复任务延迟 ≤ 期间的 10%(上限 15 分钟),一次性任务在 :00/:30 最多提前 90 秒;教学版无。④ 生命周期:CC 重复任务 7 天自动过期(可配置,上限 30 天)、MAX_JOBS=50 上限;教学版无。⑤ 触发注入:CC 以 priority:'later' + WORKLOAD_CRON 低 QoS 入队;教学版直接 append。⑥ queue processor:CC 还处理 UI 阻塞、队列优先级、不同消息模式;教学版只保留空闲交付。⑦ cron 语法:CC 支持 N-M/S,教学版不支持 L/W/? 等。

## 与 CC 的差距(教学版刻意简化)

- 工具名与开关:CC 三件套 + feature gate/GrowthBook;教学版三件套,无开关。
- 并发安全:CC 有 .scheduled_tasks.lock 防多 session 重复触发;教学版只有进程内 cron_lock。
- 防惊群抖动:CC 有(重复任务 ≤10%/15min,一次性 :00/:30 提前 90s);教学版无。
- 生命周期:CC 有 7 天过期 + MAX_JOBS=50;教学版无。
- 交付优先级:CC 用 priority:'later' + WORKLOAD_CRON 低 QoS;教学版直接入队。
- queue processor:CC 处理 UI 阻塞、队列优先级、不同消息模式;教学版只做空闲交付。
