s05 到 s06
s05 解决的是“一个 agent 会跑偏”，办法是显式计划。
s06 解决的是“一个 agent 即使有计划，也不该把所有中间调查过程都塞进主上下文”，办法是把子问题委派给一个 全新 messages[] 的 subagent。这就是从“计划”走向“上下文隔离”。
你可以把两章的关系记成一句话：
s05 管步骤，s06 管注意力。

s06 相比 s05，新增的核心能力是什么？它解决的具体问题是什么？
避免上下文污染, 避免了任务所有中间调查过程都塞进主上下文, 具体操作将任务委托子agent. 新开上下文, 任务完成再把总结结果返回给父agent. 父子agent上下文是隔离的

task 工具和 todo_write 工具在架构上的共同点是什么？为什么 task 也不需要专门的新调度入口？
任务计划, task 仍然只是一个普通工具
它们在架构上都只是普通工具：都在 TOOLS 里声明 schema，都在 TOOL_HANDLERS 里注册 handler，都通过同一个 dispatch 机制执行。也就是说，新增能力不需要新入口，只要现有 tool protocol 能承载它。todo_write 的 handler 是 run_todo_write，task 的 handler 是 spawn_subagent，但调用协议没变，

spawn_subagent() 里最关键的一行代码是哪一行？为什么它能体现“上下文隔离”？
messages = [{"role": "user", "content": description}]  # fresh context

为什么子 agent 只返回最终摘要，而不是把整个 messages[] 都回传给父 agent？
大部分中间调查过程跟任务最终目标没关系. 如果这些中间调查过程占着messages, 会让 Agent 越来越"健忘"，它记不住最初的问题是什么了。

为什么子 agent 不能再拥有 task 工具？这只是为了“简单”吗，还是有更本质的系统原因？
防止子 Agent 再 spawn 新的子 Agent
防止子 Agent 再 spawn 新的子 Agent 是现象，背后的系统原因是 限制递归展开和资源失控。如果子 agent 还能继续 task -> task -> task，会带来三类问题：上下文树无限扩张、调度复杂度飙升、成本和安全边界更难控制。所以这不只是“为了简单”，而是为了给系统加一个明确的结构边界。代码上就是 SUB_TOOLS 里没有 task


s06 里，什么东西被隔离了，什么东西没有被隔离？上下文隔离, hook(安全策略等)没有隔离, 
隔离了：消息历史、注意力空间、中间调查过程
没隔离：文件系统改动、命令执行结果造成的真实影响、hooks/权限策略

为什么说 s06 的主 loop 仍然没变？同一套dispatch机制, tool 协议新增task工具. 主 loop没变
子 agent 的工具调用为什么还要走 PreToolUse hook？hook不隔离, 安全策略不跳过
上下文隔离不代表安全隔离。如果子 agent 能绕开 PreToolUse，那它就成了权限旁路，整个 harness 会被架空。所以子 agent 也必须复用同一套安全入口

s06 相比 s05，最大的收益是“更聪明”还是“更干净”？为什么？ 更干净, 过滤掉大部分中间调查信息, 大部分中间调查信息跟任务目标无关


如果子 agent 只返回摘要，那父 agent 怎么验证子 agent 说的结论是不是对的？不知道
第 1 题，父 agent 的验证方式不是“相信摘要”，而是 把摘要当成线索，再用自己的工具重新检查关键事实。
比如子 agent 返回“这个项目用 pytest”，父 agent 可以再自己 read_file 看 requirements.txt、pyproject.toml 或 tests/ 目录；如果子 agent 返回“我已经创建了文件”，父 agent 可以自己再 glob 或 read_file 验证。
也就是说：
子 agent 负责压缩调查过程，父 agent 负责决定是否复核关键结论。
这就是为什么 README 里的示例会写成 “子 agent 创建文件，然后由父 agent verify”，见 [README.md (line 126)](/Users/bytedance/Downloads/te/learn-claude-code/s06_subagent/README.md:126)。
