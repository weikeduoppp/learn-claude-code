# 学习地图

## s14 到 s15

`s14` 解决的是“任务什么时候自动触发”。

`s15` 解决的是“一个 Agent 不够时，多个 Agent 怎么长期协作”。

一句话记住：

> `s14` 管时间调度，`s15` 管团队协作。

再压成一句：

> 从“什么时候做”，进入“谁和谁一起做”。

---

## 本章解决什么问题

这章的敌人不是“不会拆任务”，而是：

- 一个 Agent 的上下文和注意力覆盖不了整个大项目
- `s06` 的 subagent 只适合一次性任务，不适合长期协作
- 多个执行单元之间缺少稳定通信方式
- Lead 看不到队友完成了什么，也没法持续协调

所以 `s15` 解决的不是“再加一个子 agent 工具”，而是：

> 把一次性 delegation，升级成可长期存在、可异步通信的 Agent 团队。

---

## 相比 s14 新增了什么

相对 `s14`，这章新增的是**团队通信与持久队友**，不是调度器增强。

新增的核心能力有：

- 文件收件箱 `MessageBus`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s15_agent_teams/code.py:604)
- 队友线程启动器 `spawn_teammate_thread()`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s15_agent_teams/code.py:645)
- Lead 可用的新工具：`spawn_teammate`、`send_message`、`check_inbox`
- 队友自己的简化工具集：`bash`、`read_file`、`write_file`、`send_message`
- Lead 每轮结束后注入 inbox 消息到 history，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s15_agent_teams/code.py:863)

一句话：

> `s15` 新增的不是“更多任务”，而是“多个长期存在的工作脑子”。

## 核心设计

### 1. 队友不是一次性 subagent

`s06` 的 subagent 是“做完就走”的临时工。  
`s15` 的 teammate 是“可以多轮工作、随时收发消息”的长期成员。

这个区别不在“是不是子线程”，而在：

- 是否保留自己的执行循环
- 是否保留自己的上下文
- 是否能通过收件箱继续接收新信息

### 2. MessageBus 是最小消息总线

`MessageBus` 的本质不是“写文件”，而是：

> 给每个 Agent 一个独立收件箱，让 Agent 之间可以异步收发消息。

教学版用 `.mailboxes/*.jsonl` 做文件收件箱，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s15_agent_teams/code.py:604)。

这样设计的好处：

- 跨线程容易观察
- 调试直观
- 不需要额外服务

### 3. Lead 和队友不是同一个 loop

Lead 有自己的主循环。  
每个队友也有自己的简化循环，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s15_agent_teams/code.py:645)。

所以这章最关键的变化是：

- 不是一个 loop 管所有人
- 而是多个 loop 通过消息总线协作

### 4. 队友结果必须重新注入 Lead history

队友发来的结果不能只打印到终端。  
如果不注入 Lead 的 `history`，Lead 的 LLM 就看不到队友做了什么。

所以 inbox 注入的本质是：

> 让“队友完成的外部事实”重新变成 Lead 可推理的上下文。

### 5. 教学版的 10 轮限制只是防失控

队友线程在教学版里最多跑 10 轮，不是协议本质，只是防止示例无限循环。

这说明一个重要点：

> `s15` 真正想教的是团队通信机制，不是生命周期管理的最终形态。

生命周期的进一步升级，是 `s16` 的内容。

## 为什么这样设计

### 为什么不用内存队列，偏偏用文件收件箱？

因为教学版要优先强调“可观察”和“跨线程真实存在的消息”。

文件收件箱的好处：

- 人能直接看到消息长什么样
- 不依赖进程内共享引用
- 能把“通信”这件事从代码变量里拉到外部状态里

### 为什么队友工具集比 Lead 小？

因为教学版想先聚焦：

- 如何通信
- 如何分工
- 如何回报结果

而不是一上来把所有系统能力都同步给队友。

### 为什么 Lead 需要 `check_inbox`，还要自动注入？

因为这是两层能力：

- `check_inbox`：显式查看
- 自动注入：让模型自然接收到队友结果

它们不是重复，而是“人工查看”和“模型感知”的两条路径。

## 关键知识点

1. `s15` 升级的是协作模型，不是任务模型。
2. `MessageBus` 的本质是异步收件箱，不是简单文件写入。
3. 队友是长期存在的执行单元，不是一次性 subagent。
4. Lead 和队友各自有 loop，通过消息总线协作。
5. 队友结果只有重新注入 Lead history，Lead 的 LLM 才能继续协调。
6. 教学版 10 轮限制是防失控，不是协议本质。

`s06` 是一次性 delegation。  
`s15` 是长期协作关系。

所以：

- `s06` 解决上下文隔离

## 扩展点与局限

### 教学版的扩展点

- 加入更完整的队友工具集
- 加入权限审批冒泡
- 加入 idle/heartbeat 机制
- 加入任务看板共享

### 教学版的局限

- 文件收件箱没有严格并发锁
- 队友轮数有限，不适合长期常驻
- 没有正式的 shutdown 协议
- Lead 端的 inbox 处理比较粗糙

## 参考答案

### 第一轮参考答案

1. `s15` 新增的是长期存在的多 Agent 协作能力。它解决的是单个 Agent 注意力不足、上下文覆盖不全时，多个执行单元怎么并行工作并持续通信。
2. `s06` 的 subagent 适合一次性调查或隔离执行，但做完就销毁，不能长期协作、不能持续收发消息、不能形成团队工作关系。
3. `MessageBus` 是异步收件箱系统。它让 Agent 之间可以通过独立 inbox 传递消息，从而把协作从“共享上下文”变成“消息总线”。
4. 因为打印只对人可见，不对 Lead 的 LLM 可见。只有注入 history，队友的结果才会变成 Lead 后续推理和协调的上下文。
5. 提升的是协作执行能力，不是模型推理能力。模型没有变聪明，系统只是多了队友、收件箱和并行协作机制。

### 第二轮参考答案

1. 队友需要自己的 loop，因为它是独立执行单元，要自己接消息、调模型、调工具、推进工作，而不是由 Lead 同步代跑。
2. 因为共享 messages 会把多个 Agent 的上下文混在一起；独立 inbox 才能保持通信边界和责任边界。
3. 因为教学版先聚焦“团队通信机制”，避免一开始把任务、cron、权限等复杂度全部压到队友身上。
4. 主循环协议没变，每个 Agent 各自仍然是 `messages -> llm -> tool_use -> tool_result -> messages`。变的是系统里 Agent 的数量和它们之间的消息连接方式。

### 第三轮参考答案

1. 因为队友不是一次调用完就消失，它有自己的上下文、自己的循环、自己的 inbox，可以在多轮里持续工作和接收消息。
2. 多线程只是实现方式；真正的设计升级是 Agent 之间可以通过异步消息持续协作。
3. 因为光能发消息还不够，消息还需要结构化约定，特别是在关机、审批、请求-响应这类场景里。
4. `s15` 的设计本质，是把单脑执行升级成多个长期执行单元通过异步收件箱协作的系统。
