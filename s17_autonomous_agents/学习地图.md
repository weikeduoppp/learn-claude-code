# 学习地图

## s16 到 s17

`s16` 解决的是“队友之间怎么按协议协作”。

`s17` 解决的是“为什么任务还得由 Lead 手工分配，队友能不能自己认领”。

一句话记住：

> `s16` 管协议协商，`s17` 管自治认领。

再压成一句：

> 从“等人安排活”，进入“自己看板、自己找活”。

---

## 本章解决什么问题

这章的敌人不是“不会通信”，而是：

- Lead 仍然是任务分配瓶颈
- 队友完成工作后没有自动找下一个任务的能力
- 看板上有任务，但队友不会主动认领
- 系统缺少“空闲时自组织”的机制

所以 `s17` 解决的不是“让队友多跑几轮”，而是：

> 把队友从被动执行者升级成会自己看板、自己认领的自治工作单元。

---

## 相比 s16 新增了什么

相对 `s16`，这章新增的是**空闲通知 + task watcher + 空闲轮询 + 自动认领**。

核心新增：

- `scan_unclaimed_tasks()`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s17_autonomous_agents/code.py:341)
- `task watcher`，监听 `.tasks/` 稳定变化后唤醒 idle 队友
- `idle_poll()`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s17_autonomous_agents/code.py:436)
- `idle_notification`，队友进入 IDLE 时会先通知 Lead
- 队友生命周期从单纯 work 扩展成 `WORK -> IDLE -> SHUTDOWN`
- `claim_task()` 增加 owner 检查，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s17_autonomous_agents/code.py:107)
- `release_task()` 可把残留的 `in_progress` 任务退回 `pending`
- 队友工具集加入 `list_tasks`、`claim_task`、`release_task`、`complete_task`

一句话：

> `s17` 新增的不是“更多协议”，而是“队友自己找活干”的能力。

## 核心设计

### 1. 自治的前提不是更聪明，而是空闲轮询

队友要能自治，前提不是模型更强，而是系统给它一个空闲阶段去检查：

- inbox 有没有新消息
- 任务板上有没有可认领任务

而且现在进入空闲前会先发 `idle_notification` 给 Lead，告诉系统“我现在可分配了”。

进入 IDLE 后，又多了一层 task watcher：

- 新任务创建时，唤醒 idle 队友立即重查
- 依赖任务完成、某个任务从 blocked 变成可启动时，也会触发重查
- 依赖判断仍然是：`blockedBy` 中没有未完成任务，而不是 `blockedBy` 为空

所以这章的起点不只是 `idle_poll()`，而是：

- 先通知自己已空闲
- 再开始轮询 inbox 和任务板

### 2. inbox 优先，任务板其次

`idle_poll()` 里先看 inbox，再看任务板，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s17_autonomous_agents/code.py:436)。

这个顺序非常关键，因为：

- inbox 里可能有 shutdown_request 等控制消息
- 控制消息优先级高于“继续找活”

一句话：

> 自治不是乱抢任务，先响应控制协议，再处理任务板。

### 3. 自动认领的本质是把任务板变成可扫描的外部状态

`scan_unclaimed_tasks()` 只看满足这几个条件的任务：

- `pending`
- 无 `owner`
- `can_start()` 为真

这说明自治不是“模型自己猜哪些任务能做”，而是：

> 队友根据外部真实状态扫描可执行任务。

### 4. 生命周期从两段变三段

这一章最重要的抽象之一是：

- WORK：执行当前任务
- IDLE：检查 inbox 和任务板
- SHUTDOWN：退出并汇报

这意味着队友不再是“做完当前任务就结束”，而是“做完后先看看还有没有下一个任务”。

### 5. 身份重注入是对 compaction 的补偿

教学版里 messages 可能被压缩掉，导致队友“忘了自己是谁”。  
所以每轮重新进入 WORK 时，会在必要时重注入身份信息。

这说明一个重要工程点：

> 自治不是只靠生命周期，还要兼顾上下文稳定性。

## 为什么这样设计

### 为什么不让 Lead 继续手工 assign？

因为 Lead 会成为吞吐瓶颈。  
当任务数增长时，Lead 不应该浪费注意力去做重复分配动作。

### 为什么自治认领不能只看 `pending`，还要检查 owner 和依赖？

因为可认领不等于“列表里存在”。  
真正能开工必须满足：

- 没有人在做
- 状态还是 `pending`
- 依赖已完成

这让自治认领仍然受系统规则约束。

### 为什么要有 IDLE_TIMEOUT？

因为教学版不希望队友永远挂着空轮询。  
超时退出是资源控制手段，不是自治本质。

## 关键知识点

1. `s17` 升级的是任务分配方式，不是协议方式。
2. 自治依赖两件事：空闲轮询和可扫描的任务板。
3. inbox 优先于任务板，说明控制消息优先于继续找活。
4. 自动认领仍然受 owner 和依赖约束。
5. 队友生命周期从执行型线程升级成工作型线程。
6. `idle_notification` 让 Lead 显式知道队友已经空闲。

## 扩展点与局限

### 教学版的扩展点

- 更复杂的任务选择策略
- 优先级和抢占
- 更可靠的并发 claim 锁
- idle heartbeat
- 更正式的 `fs.watch()` / 事件驱动 watcher

### 教学版的局限

- 没有文件锁，自动认领有竞争风险
- 任务选择策略很简单
- idle timeout 固定
- 身份重注入是教学补偿，不是最优方案
- 如果 worker 异常退出，通常仍要靠 `release_task` 人工把残留任务放回看板
- task watcher 仍然是目录快照轮询 + debounce，不是真正的文件系统事件流

## 错误认知

戳中了 README 那句话的逻辑漏洞——"CC 保留 system prompt 所以不用重注入，教学版需要手动处理"这个说法不成立，因为教学版的 system prompt 也是独立变量、同样保留。所以这个解释是错的/至少是不完整的。
真正让 CC 不需要重注入的，是它有一套内建的跨压缩上下文延续机制，教学版没有。拆开看三层：
第一层：system prompt——两者都保留，无法区分
CC 和教学版一样，system 每次请求都原样带上，身份本体都不丢。这一层上两者平手。
第二层：压缩摘要——CC 的摘要是"延续体"，教学版的摘要是"一次性总结"
- CC 的 autoCompact 摘要生成是结构化的，摘要文本本身就是要"接着干"的载体——目标、进度、约束都被要求写进去，压缩后的历史天然带着"我在做什么"。
- 教学版 s08 的 summarize_history 虽然也要求保留 goal/files/remaining work/constraints，但它是一次性的 LLM 总结，质量靠临场发挥，而且输入只有 messages、不含 system——摘要里不会出现"我是 alice、我是后端开发者"这类角色信息。
第三层：session memory——真正的分水岭
- CC 有 s09 讲过的 session memory：持续维护的会话状态文件，压缩前先读它，内容足够（≥10K token、≥5 条消息）就直接拿 session memory 当摘要，连 LLM 总结都省了。它天然包含"我是谁、目标、进度"，压缩后依然存活。这是专门为"压缩不失忆"设计的一层。
- 教学版 s17 没有这层。压缩完，历史就只剩一段摘要，没有别的延续来源。
所以正确的说法应该是：CC 不需要重注入，因为它的压缩链路里，上下文连续性由"system prompt 原样保留 + 结构化摘要 + session memory"三样共同兜底；教学版只有第一样，所以只能事后用 len <= 3 探测压缩事件，再塞一个锚点补救。
还有一个更本质的角度：重注入里那句 Continue your work 才是灵魂，而 CC 把它内建进了摘要本身——CC 压缩后的第一条消息就是"继续以下工作"式的延续指令，不需要再补。教学版 s08 的摘要其实也有类似效果（[Compacted]\n\n{summary}），所以重注入严格说是双保险，演示价值大于实用价值。
结论：不是"CC 保留 system prompt 所以不用"，而是"CC 的压缩自带延续设计，教学版没有，只能用重注入补"。README 那句解释值得打个问号。

## 三轮问答

验收标准（学完自测）
1. 队友三阶段生命周期？每阶段的进入条件和退出条件？ WORK → IDLE → SHUTDOWN 
WORK -> 领取任务 退出 SHUTDOWN/完成任务
IDLE -> 完成任务 退出 SHUTDOWN/60秒超时
SHUTDOWN -> 进入它的原因是"收到关机请求或超时"，不是被动等指示。

完成任务后去的是 IDLE，不是 SHUTDOWN。WORK 阶段 stop_reason != "tool_use"（活干完）→ break → 进入 IDLE 等下一个任务；只有 WORK 阶段收到 shutdown_request（should_shutdown=True）才直接去 SHUTDOWN。

IDLE 的退出有三个分支，你漏了"work"：返回 work（收到新消息或认领成功）→ 回 WORK；返回 shutdown（收到关机请求）→ 退出；返回 timeout（60s）→ 退出。你只写了 shutdown/超时。
SHUTDOWN 不是"等 lead 指示"：它是退出阶段，干的事是发 summary（BUS.send(..., "result")）、清 idle_teammates、pop active_teammates。进入它的原因是"收到关机请求或超时"，不是被动等指示。

正确版本：WORK（领取/收信 → 干活 → 干完 或 收到 shutdown）→ IDLE（发 idle_notification → 轮询，有新活回 WORK / 收到 shutdown 退出 / 60s 超时退出）→ SHUTDOWN（发总结，清理，退出）。


2. idle_poll 的检查顺序是什么？为什么 inbox 必须优先于任务板？
SHUTDOWN -> inbox -> 任务板  inbox更重要
idle_poll 第一步是 wait 等唤醒，然后读 inbox，inbox 里 shutdown_request 最先处理，其次普通消息，最后才是任务板。

inbox 优先的原因：协议消息（关机、派活）比新任务紧急——关机请求不及时处理，队友可能又去认领新任务白干。

3. 两种唤醒源（task watcher / 5s 轮询）各自解决什么问题？为什么不能只留一个？
task watcher 当任务列表新增任务了. 唤醒空闲的队友, 为了当新增任务了. 没有在线队友处理, 需要用户手动重新指派了
5s 轮询 队友进入idle时, 轮询查询任务列表是否剩下的任务.

为什么不能只留一个"没答到点：watcher 管及时（变化立刻响应），轮询管可靠（watcher 可能漏事件——教学版是快照比较不是真 fs.watch，更容易漏）；只留轮询则最坏延迟 5s。

4. scan_unclaimed_tasks 的三个条件？"有 blockedBy 依赖"的任务能不能被认领，条件是什么？ pending + 无 owner + can_start
依赖语义：blockedBy 非空不代表不能做，只有存在未完成的前置任务才不能做（"blockedBy 中没有未完成"而非"blockedBy 为空"）。
5. claim_task 的 owner 检查解决什么问题？教学版没有文件锁，两个队友同时抢同一任务会怎样？防止同一任务多人处理,已有owner, 认领失败的队友去找下一个
6. release_task 什么时候需要？它解决什么故障场景？队友崩溃/超时后任务卡在 in_progress，需要手动放回 pending 让别的队友认领—
7. 身份重注入为什么用 len(messages) <= 3 判断？触发场景是什么？CC 为什么不这么干？防止system prompt丢失
8. consume_lead_inbox 干什么？为什么 check_inbox 工具和主循环末尾都调它？让LLM知道上下文
太简略。consume_lead_inbox 干两件事：① 路由协议 response 更新状态（plan 审批、shutdown 确认，走 ProtocolState/match_response）；② 把队友消息注入 Lead 的 history。两处都调是为了逻辑统一：LLM 主动查（check_inbox → tool_result）和系统自动消费（wake 后主循环）走同一个函数，协议处理和注入不重复实现。

9. 教学版和 CC 的空闲机制对比（至少 3 点：轮询间隔、watcher 实现、超时策略）。
空闲机制：教学版 = idle_notification + task watcher（快照轮询）+ idle_poll 5s 兜底；
CC = idle_notification + 500ms mailbox 轮询（waitForNextPromptOrShutdown）+ task watcher（真 fs.watch，1s debounce）+ tryClaimNextTask 主动认领。教学版已把三个机制都补进来了，watcher 仍是简化实现。

## 参考答案

### 第一轮参考答案

1. `s17` 新增的是队友空闲时自动扫描任务板并认领任务的能力。它解决的是 Lead 手工分配任务的瓶颈。
2. 因为任务多起来后，Lead 会变成任务分配器而不是协调者，系统吞吐会被 Lead 卡住。
3. `idle_poll()` 是队友空闲时的轮询阶段，用来检查 inbox 和任务板，决定是继续工作、关机还是超时退出。
4. 因为任务可认领必须同时满足“还没开始”“没人拥有”“依赖已完成”这三个条件。
5. 提升的是组织执行能力，不是模型推理能力。模型没变聪明，只是系统更会组织队友工作。

### 第二轮参考答案

1. 因为 inbox 里可能有 shutdown_request 等高优先级控制消息，必须先处理。
2. 因为队友做完当前任务后不应该直接结束，而应该先看看是否还有新工作。
3. 因为自动认领仍然受任务板的真实状态和依赖约束，不能由模型随便决定。
4. 因为每个 Agent 的 loop 结构没变，变化的是队友在 loop 之间新增了 idle 阶段和任务板扫描。

### 第三轮参考答案

1. 因为真正关键的是队友根据外部任务板和 inbox 的真实状态来决定下一步，而不是凭主观感觉自动行动。
2. 因为 `s17` 的自治认领仍然建立在 `pending/in_progress/completed` 和依赖检查之上。
3. 因为当多个队友都能同时认领任务后，必须解决它们在同一目录下互相覆盖文件的问题。
4. `s17` 的设计本质，是把队友从被动接单者升级成会根据任务板和消息状态自组织工作的执行单元。
