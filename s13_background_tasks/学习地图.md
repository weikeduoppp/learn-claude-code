# 学习地图

## s12 到 s13

`s12` 解决的是“任务怎么持久化、依赖化、可恢复”。

`s13` 解决的是“慢操作执行时，Agent 为什么不能干等，以及怎么不中断主循环地继续工作”。

一句话记住：

> `s12` 管任务图，`s13` 管执行时的异步化。

再压成一句：

> 从“任务怎么表示”，进入“任务执行时遇到慢操作，系统怎么不停摆”。

---

## 本章解决什么问题

这章的敌人不是“不会执行命令”，而是：

- 有些工具调用很慢，尤其是 `bash`
- Agent 在等慢命令返回时会空转
- 空转期间不能继续处理别的事情
- 后台任务完成后，还需要一个机制把结果重新送回主循环

所以 `s13` 解决的不是“加一个 bash 功能”，而是：

> 把慢操作从同步阻塞执行，改成后台执行 + 后续通知。

## 核心设计

### 1. 慢操作不是“失败”，而是“不要阻塞”

这章不是在处理错误，而是在处理时延。

像 `npm install`、`pip install`、`pytest`、`build` 这种命令，问题不是“执行不了”，而是“执行太久”。  
如果还按同步方式跑，Agent 会卡在工具返回点，见 [README.md](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/README.md:17)。

所以这里的设计目标是：

- 命令照样执行
- 但主循环不要停
- 结果晚点回来也没关系

### 2. 显式请求优先，启发式只是兜底

后台执行不是完全靠规则猜的，主路径是模型显式传 `run_in_background=true`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:331)。

如果模型没传，教学版再用关键词启发式兜底，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:320)。

这背后的设计原则是：

- 最好由模型按意图决定
- 系统只在必要时提供保底判断

也就是：

> 显式控制优先于隐式猜测。

### 3. 后台任务必须有独立身份

后台任务不是“模糊地跑着”，而是有一个 `bg_id`，比如 `bg_0001`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:348)。

这样做的目的有三个：

- 能追踪是哪一个后台任务
- 能在后续 turn 里引用它
- 能把“启动事件”和“完成事件”关联起来

如果没有 `bg_id`，后台结果回来时系统就不知道这条通知属于哪个异步执行单元。

### 4. 后台完成不是 tool_result，而是独立通知

这是本章最容易忽略、但很关键的点。

后台命令启动时，原始 `tool_use` 已经得到了一个占位 `tool_result`，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:437)。

等后台真正完成时，不能再拿同一个 `tool_use_id` 回一次结果，所以它必须作为独立的 `<task_notification>` 文本注入，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:382)。

这背后的原因不是“格式好看”，而是协议边界：

> 一个 `tool_use` 只能配对一个 `tool_result`。

因此后台完成事件本质上是：

- 不是工具响应
- 而是系统通知

### 5. 主循环没变，变的是工具调用后的控制流

`s13` 的 `agent_loop()` 还是同一个主循环，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:412)。

没有变的部分：

- 还是 `messages -> llm`
- 还是 `tool_use -> tool_result`
- 还是把结果写回 `messages`

变的是：

- 工具有两种执行路径：同步 / 后台
- 同步路径直接拿输出
- 后台路径先返回占位，再在后续轮次注入通知

所以这章继续证明：

> loop unchanged，execution strategy changed。

## 为什么这样设计

### 为什么后台化挂在 dispatch 外层，而不是塞进 `run_bash()`？

因为“是否后台执行”不是 bash 自己的局部实现细节，而是**调度决策**。

`run_bash()` 只负责执行命令，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:186)。  
决定同步还是后台，是 `agent_loop()` 在看到 tool call 之后做的，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s13_background_tasks/code.py:435)。

这和前面几章是一致的：

- tool 做局部能力
- loop 外围做调度和控制

### 为什么不把后台结果直接塞回原来的工具返回？

因为原工具调用已经结束，模型已经收到过占位结果。  
后台完成是新的事件，不是原事件的“补丁”。

如果硬复用原 `tool_use_id`，会破坏工具协议的一一配对关系。

### 为什么教学版用线程和内存字典？

因为这章要讲的是“后台执行 + 通知注入”的最小模型，不是完整任务基础设施。

线程 + 内存字典的好处：

- 简单
- 可观察
- 容易把执行、完成、回注三段讲清楚

它不是生产级方案，只是教学上最小闭环。

## 关键知识点

1. `s13` 不是新增业务工具，而是改工具执行方式。
2. 后台执行的主路径是 `run_in_background` 显式参数，不是关键词猜测。
3. 后台任务启动时先返回占位 `tool_result`。
4. 后台任务完成时返回的是独立通知，不是第二次 `tool_result`。
5. `<task_notification>` 的本质是“异步完成事件”。
6. `bg_id` 是后台任务的身份标识，不是装饰字段。
7. 后台任务让 Agent 在慢操作期间继续利用时间，而不是干等。

## 扩展点与局限

### 教学版的扩展点

- 后台任务可以扩展到不只是 `bash`
- 可以加入取消、停止、重试
- 可以把后台状态落盘，而不是只存在内存里
- 可以把通知放入真正的队列，而不是每轮轮询收集

### 教学版的局限

- 后台任务状态不持久化，进程退出就丢
- `daemon` 线程退出时任务也会跟着丢
- 没有取消 / 暂停 / 查看增量输出
- `is_slow_operation()` 是启发式，不够可靠
- 只有在后续轮次里才有机会把通知重新注入

这些局限不是 bug，而是教学版刻意留白。

- 让模型把它当成“新的输入事件”处理

结果当然包含在里面，但主循环接收到的首先不是“旧工具的补结果”，而是“某个异步任务完成了”这件事。
所以它必须作为一个新的输入事件进入 messages，而不是修改历史。
一句话：
主循环消费的不是补丁，而是新事件。

3. s13 为什么会自然通向 s14？“后台完成后通知”还缺什么能力？
- 后台任务状态不持久化，进程退出就丢
- `daemon` 线程退出时任务也会跟着丢
- 没有取消 / 暂停 / 查看增量输出
- `is_slow_operation()` 是启发式，不够可靠
- 只有在后续轮次里才有机会把通知重新注入
定时能力
如果不是“稍后完成时通知”，而是“未来某个时间点再启动”，怎么办？
s13 已经解决了“现在启动，稍后通知”，但还没有解决“未来某个时间点再启动”。
所以 s14 补的不是后台化本身，而是：
- 定时触发
- 周期触发
- 不依赖当前会话正在活跃
一句话：
s13 解决异步完成，s14 解决定时开始。

4. 用你自己的话总结一句：s13 的设计本质是什么？不要说 “background tasks”。
s13 的设计本质是让慢操作从阻塞式工具调用，变成带占位结果和后续通知的异步事件。
我帮你修成最终标准版：
s13 的设计本质，是把慢操作从“一次调用必须当场返回结果”，改成“先确认启动、后以事件形式回注完成”的两阶段执行协议。`
这一章你可以收官了。
最后把 s13 压成 4 句话记住：
- s13 升级的不是工具种类，而是工具执行模型。
- 后台启动先返回占位结果，真正完成时再以通知形式进入主循环。
- 线程不是本质，通知和事件回注才是本质。
- s13 自然通向 s14，因为“稍后完成”之后，下一个问题就是“未来何时启动”。
