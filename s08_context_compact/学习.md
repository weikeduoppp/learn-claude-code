# s08 学习地图:Context Compact

## 1. 这一章在对抗什么

Agent 跑着跑着不动了——不是能力问题,是上下文满了。每条命令输出、每个文件内容全堆在 `messages` 里,上下文窗口有限,满了之后 API 直接拒绝:`prompt_too_long`。

解决方案:在每轮 LLM 调用前插入四层压缩管线。核心设计一句话:**便宜的先跑,贵的后跑**。

## 5. 必须理解透的设计决策

**顺序不能换。** L3(budget)在 L2(micro)前面:micro 会把旧的大 tool_result 替换成一行占位符,完整内容就没了;budget 必须在此之前把内容落盘。CC 源码同样把 `applyToolResultBudget` 放最前。

**配对保护。** 所有切消息的地方(包括 reactive)都要保证 `assistant(tool_use)` 和后面的 `user(tool_result)` 不被拆开——API 硬性要求,拆开就报错。

**压缩前先落盘。** `write_transcript` 把完整对话写成 JSONL 到 `.transcripts/`;压缩是破坏性操作,transcript 保留可恢复记录。但教学版没有检索工具,模型上下文里只剩摘要。

**防失控。** auto 摘要熔断(连续失败 3 次停,README 设计,CC 里是 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3`);reactive 重试上限 1 次,超过抛异常交给 s11;API 调用成功后 `reactive_retries` 清零。

**教学版简化(刻意)。** token 用字符数估算;micro 用文本占位而不是 API 层 `cache_edits`;没有 readFileState、没有压缩后恢复、没有 contextCollapse/sessionMemoryCompact。

## 7. 进阶对照(README 附录)

- 执行顺序:教学版 budget → snip → micro → auto;CC 是 budget → snip → micro → **collapse** → auto(`query.ts:379-468`),教学版没有 contextCollapse。
- snip:教学版按条数(头 3 + 尾 47);CC 仅主线程启用,`snipCompactIfNeeded` 返回 `{ messages, tokensFreed, boundaryMessage? }`,还暴露 `SnipTool` 让模型主动调。
- micro:教学版按位置保留最近 3 条;CC 有 time-based(60 分钟)和 cached(按计数)两条路径,legacy path 已移除。
- 压缩后恢复:教学版只留摘要;CC 按预算重新附加最近文件(最多 5 个 × 5K token,总 50K)加计划/agent/skill/tool 上下文。
- 阈值:教学版字符估算 50K;CC 精确 token:`contextWindow - maxOutputTokens - 13_000`。
- 摘要要求:教学版 5 类信息;CC 9 个部分 + `<analysis>`/`<summary>` 双标签,且首尾双重禁止调工具。
- contextCollapse:独立上下文管理系统,启用时抑制 proactive autocompact;manual `/compact` 和 reactive fallback 不受影响。
- sessionMemoryCompact:compact_history 前先用 s09 的 session memory 做轻量摘要、不调 LLM——学完 s09 回来再看。

## 8. 验收标准(学完自测)

Q1: 四层压缩分别解决什么问题?为什么说"便宜的先跑,贵的后跑"?

A: L1 裁旧消息、L2 旧结果占位、L3 大结果落盘都是纯结构操作,0 API;L4 才调 LLM 摘要(1 API);reactive 是 API 报错后的最后兜底。成本从低到高排列,触发从主动到被动。

Q2: 执行顺序为什么是 budget → snip → micro,不能换?

A: micro 会把旧的大 tool_result 替换成一行占位符,完整内容就没了;budget 必须在此之前把内容落盘,否则落盘逻辑永远拿不到完整内容。CC 源码同样把 `applyToolResultBudget` 放最前。

Q3: snip_compact 和 reactive_compact 为什么都要检查 tool_use/tool_result 配对?

A: API 要求 tool_use 之后必须紧跟对应 tool_result;切口若落在二者之间会产生孤立块,API 报错。snip 在头尾两个切口都做保护,reactive 切尾部 5 条时做同样的检查。

Q4: compact_history 和 reactive_compact 有什么区别?

A: 触发方式:auto 主动(每轮前字符估算超 50K,或模型调 compact 工具),reactive 被动(API 报 prompt_too_long 后)。压缩策略:auto 把全部消息换成一条摘要(可能丢最近细节),reactive 只总结较早历史、保留最近约 5 条原始消息,更温和。重试:auto 熔断 3 次(CC 的 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES`),reactive 上限 1 次,超过抛异常。

Q5: 为什么压缩前要写 transcript?教学版和 CC 在"压缩后恢复"上差在哪?

A: 压缩是破坏性操作,transcript(JSONL)保留可恢复的完整记录,但教学版没有检索工具,模型上下文里只剩摘要。CC 压缩后会按预算重新附加最近文件(5 个 × 5K token,总 50K)以及计划、agent/skill/tool 上下文。

Q6: compact 工具是干什么的?模型主动调用时 agent_loop 做了什么?

A: 它是 s08 新增的第 9 个工具,让模型在上下文紧张时主动请求压缩。agent_loop 检测到 `block.name == "compact"` 就执行 compact_history,回填 tool_result 为 `[Compacted...]` 并 append,然后 break 结束当前轮,用压缩后的上下文开始新一轮。

Q7: 熔断器和重试上限防什么?

A: 防"压缩失败 → 重试 → 再失败"死循环烧 API。reactive 超上限直接抛异常,完整错误恢复留给 s11;API 调用成功后重试计数清零,说明系统恢复健康。

**速记:** 四层 = 裁中间 → 旧结果占位 → 大结果落盘 → LLM 摘要;顺序 budget→snip→micro 不能换;配对保护防孤立 tool_result;transcript 保证可恢复;auto 熔断 3 次、reactive 重试 1 次;compact 工具让模型主动压缩。

为什么 snip_compact 不能简单粗暴地随便删消息？ 保留近期3条会话数据 好衔接对话
不能把 assistant(tool_use) 和后面的 user(tool_result) 拆开。
如果随便删，很可能会留下一个孤立的 tool_result，或者留下一个没有结果的 tool_use，这样对话结构就坏了，模型看到的历史会不自洽。
所以 snip_compact 真正在保护的是：

工具调用配对完整性
更标准的答案是：
因为压缩不能破坏消息结构，尤其不能拆开 tool_use / tool_result 这一对。

micro_compact 和 tool_result_budget 的区别到底是什么？ tool_result_budget 将内容大的工具结果存储到硬盘. 只保留tool_use, tool_result路径映射. micro_compact是将旧的tool_result换成占位符.
micro_compact：处理“旧结果还在上下文里占空间”
做法是把旧 tool_result 内容替换成占位符
tool_result_budget：处理“当前这批结果太大，单次就可能把上下文撑爆”
做法是把大内容落盘，只在上下文里留路径和预览
一句话区分：
micro 是缩旧结果，budget 是搬走大结果。


为什么 L1/L2/L3 都不能替代 L4 compact_history？L1/L2/L3 是机械整理，L4 才是语义提炼。
L1/L2/L3 都只是结构和文本层面的整理，它们不理解“哪些信息对后续任务最关键”。
只有 L4 compact_history 会真正提炼：
当前目标
关键发现
已改文件

reactive_compact 和 compact_history 的关系是什么？为什么要同时存在？reactive_compact是API返回 prompt_too_long压缩处理 compact_history是上下文压缩了还超出阈值,进行保存 transcript, LLM 生成摘要, 替换消息列表
compact_history：主动、常规、阈值触发的全量摘要
reactive_compact：被动、应急、API 已经报 prompt_too_long 后的补救路径
更精炼一点可以说：
compact_history 是预防，reactive_compact 是抢救。


s08 为什么说“便宜的先跑，贵的后跑”？
先用 不需要额外 API 调用 的方法处理大部分上下文膨胀问题，只有这些低成本手段都不够时，才调用 LLM 做高成本摘要。
具体就是：
snip_compact：纯结构裁剪，0 API
micro_compact：纯文本占位，0 API
tool_result_budget：落盘替换，0 API
compact_history：真正调一次 LLM，总结历史，1 API
所以本质上是在做两件事：
省钱：能不用模型就先不用模型
保真：先做最小破坏的结构整理，不够再做语义压缩
一句话压缩就是：
先用机械手段腾空间，实在不够再让模型理解并总结。


compact 工具为什么被单独 special-case，而不是直接塞进 TOOL_HANDLERS？它需要控制两件普通 handler 控制不了的东西：
**全局状态**：不是只处理 block.input，而是重写整个 messages
**循环流程**：不是返回结果后继续当前 turn，而是结束当前 turn，下一轮再继续
这就是为什么它被 special-case 在 loop 里，而不是放进 TOOL_HANDLERS。
你可以把它记成一句话：
**TOOL\_HANDLERS 适合“函数型工具”，compact 属于“控制流型工具”。**
这就是为什么它被 special-case 在 loop 里，而不是放进 TOOL_HANDLERS。
