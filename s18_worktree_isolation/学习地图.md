# 学习地图

## s17 到 s18

`s17` 解决的是“多个队友怎么自治认领任务”。

`s18` 解决的是“多个队友认领后，在哪个目录里工作才不会互相覆盖”。

一句话记住：

> `s17` 管谁做，`s18` 管在哪做。

再压成一句：

> 从“任务归谁”，进入“工作目录如何隔离”。

---

## 本章解决什么问题

这章的敌人不是“不会分任务”，而是：

- 多个 Agent 在同一个工作目录里写文件会互相覆盖
- 改动无法按人或按任务隔离
- 清理、保留、回滚都变得困难

所以 `s18` 解决的不是“再多一个 git 工具”，而是：

> 把任务绑定到独立工作目录，让并行执行互不干扰。

---

## 核心设计

### 1. 任务系统解决的是目标，不是目录

`s12` 到 `s17` 一直在解决：

- 任务是什么
- 谁来做
- 如何协作

但没有解决：

> 同时做这些任务的人，是否在同一个目录里互相踩文件。

`s18` 补的是这个缺口。

### 2. worktree 绑定到任务，而不是绑定到 Agent

教学版把 `worktree` 写进 task 字段，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s18_worktree_isolation/code.py:67)。

这意味着：

- 隔离单位是任务
- Agent 认领任务后，自动进入对应目录

这比“给每个 Agent 固定一个目录”更合理，因为工作空间应该跟工作目标绑定。

### 3. bind 不等于 claim

`bind_task_to_worktree()` 只写 `worktree` 字段，不改任务状态，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s18_worktree_isolation/code.py:209)。

这是这章非常关键的设计点：

- bind：准备工作空间
- claim：真正开始工作

如果 bind 就顺手改成 `in_progress`，会把“准备环境”和“开始执行”混成一件事。

### 4. 队友的工具 cwd 会随任务切换

队友认领带 worktree 的任务后，自己的 `bash/read/write` 会在对应 worktree 目录下执行。  
这说明本章真正的隔离不只是“创建了目录”，而是：

> 工具执行上下文跟着任务绑定一起切换。

### 5. remove 和 keep 体现的是生命周期管理

worktree 不是只负责创建，还要负责收尾。

两条路径：

- `keep_worktree()`：保留目录和分支，待 review
- `remove_worktree()`：清理目录和分支

这说明 worktree 不是临时副产物，而是完整生命周期对象。

### 6. 安全边界很重要

`validate_worktree_name()` 限制了 worktree 名称，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s18_worktree_isolation/code.py:158)。

`remove_worktree()` 默认也会拒绝删掉有改动的目录，见 [code.py](/Users/bytedance/Downloads/te/learn-claude-code/s18_worktree_isolation/code.py:231)。

所以这章的一个重要主题是：

> 隔离不仅是并发问题，也是安全边界问题。

## 为什么这样设计

### 为什么 worktree 绑定任务，而不是绑定用户或 Agent？

因为真正需要隔离的是“任务产生的改动集合”，不是人本身。

### 为什么 bind 不改状态？

因为 worktree 是环境准备，不是执行开始。  
把这两个动作拆开，状态机会更清晰。

### 为什么 remove 默认拒绝有改动的 worktree？

因为目录隔离如果没有安全删除边界，很容易把真实工作成果误删掉。

### 为什么要记 events.jsonl？

因为 worktree 生命周期操作会影响真实文件系统和 git 状态，需要可审计。

---

## 关键知识点

1. `s18` 升级的是目录隔离，不是任务协作协议。
2. worktree 的隔离单位是任务，不是 Agent。
3. bind 是环境准备，claim 才是开始执行。
4. 工具 cwd 跟着任务 worktree 切换，才是真正隔离。
5. keep/remove 让 worktree 具备完整生命周期。
6. 名称校验和删除保护是安全边界的一部分。

## 参考答案

### 第一轮参考答案

1. `s18` 新增的是基于 git worktree 的目录隔离能力。它解决的是多个 Agent 在同一目录下并行工作时互相覆盖文件的问题。
2. 因为他们会写同名文件、共享 git 状态，导致改动互相覆盖、难以审计和回滚。
3. 因为真正需要隔离的是任务产生的改动集合，不是人本身。
4. 因为 bind 只是环境准备，claim 才是正式开工，混在一起会让状态机失真。
5. 提升的是执行隔离能力，不是模型推理能力。

### 第二轮参考答案

1. 因为只有工具执行上下文真正切换到 worktree 目录，文件写入和命令运行才会落在隔离空间里。
2. 因为 worktree 里可能还有未提交改动或未推送提交，默认拒绝是为了避免误删成果。
3. 因为 worktree 名最终会进入真实文件系统和 git 分支命名，必须阻止路径穿越和非法字符。
4. 因为主循环协议没变，变的是工具执行上下文和任务绑定的外部环境。

### 第三轮参考答案

1. 因为核心不是 git 命令本身，而是让任务拥有独立工作空间并驱动工具执行上下文切换。
2. `keep` 代表保留工作空间供后续 review，`remove` 代表安全收尾与清理生命周期。
3. 因为目录已经隔离了，下一步自然是把能力本身做成可插拔外接，而不是继续手写所有工具。
4. `s18` 的设计本质，是把任务执行从共享目录改成按任务绑定独立工作空间的模型。
